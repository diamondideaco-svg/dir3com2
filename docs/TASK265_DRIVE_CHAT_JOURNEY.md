Base: 7cd76d014166d0b53f76c4839580dc207a0f2ef6. This change is local preparation; it enables no Production configuration, provider, payment or automatic booking.

The existing USER scope and managed Drive Core remain authoritative. Cairo relative dates are resolved on the server for the current turn and returned as a validated date-only preference. The original message stays visible. Later requests replay the pinned date rather than recalculating historical “after tomorrow” against a new day. Explicit new-trip intent clears prior preferences once; a reference to the immediately preceding fresh USER proposal carries those preferences, without restoring saved-trip authority or execution consent. Bag counts are reduced from scoped USER turns, preserving conditional, refused, unknown and zero counts.

The explicit daily-chauffeur requirement-review link opens an inline chat review. Airport transfers and catalogue browsing keep their existing links; this change adds no airport-flight collection flow. The customer supplies missing endpoints/contact details, selects a published vehicle and explicitly confirms one request. No dropoff, hours, inventory or total is inferred. Creation reuses `/api/marketplace/requests` and `create_managed_drive_request`; no generic cart or second backend is involved. The shared conversation reservation and an owner-scoped opaque idempotency key prevent concurrent view/retry submissions. A lost result retains its key. The private request/review phase disables browser message persistence. Whole conversations and contact details are not copied to URLs or request notes; the earlier planning-history persistence contract remains unchanged. Only the opaque request reference/key is retained by the managed request view across reload.

The owner-only Core read projects requirements, quote, version, acceptance and notice state. It excludes supplier costs, contact details, private Operations notes and notification identifiers. An explicit approval command or button binds to the displayed reference/version. The existing atomic approval RPC performs the final ownership, version and deadline checks. Approval means that price, vehicle and validity were acknowledged; absent cancellation/change terms stay explicitly unknown. It does not issue a booking, take payment or accept unknown terms.

Two actual Auth/PostgREST lock regressions were reproduced locally: expiry and profile revocation while waiting for the context lock. The forward migration verifies the exact observed Core function-body hash, rechecks and locks active actor authority after request locks, and compares the expiry against a current database timestamp. Function EXECUTE grants remain unchanged. The expiry/revocation fixtures require a freshly owned loopback Task265 cluster and real synthetic password Auth clients; they are not shared-database setup scripts.

The current gated WhatsApp outbox can capture one Operations approval notice through an explicitly prepared continuous service. A unique scope permits at most one approved Operations recipient for that category per service; it does not select Rami and another operator by default. Existing consent, regional grants, template, activation, current-state and worker send guards remain in force. The migration enrolls nobody, activates nothing and changes no send/capture setting, budget, secret or worker binding. The legacy targeted-send route continues rejecting the new category. An owner-safe status RPC returns only a state label. Queued, provider accepted, sent and delivered remain distinct. Missing authorization means no notice; the UI reports that fact. Any future live binding/template approval, activation and delivery proof require their own authorized operational evidence.

Focused tests cover literal restored-conversation turns, Cairo calendar/UTC boundaries, genuine ambiguity and refusal, retained requirements, explicit approval intent and catalogue navigation. Local acceptance uses the full Next application with synthetic customer/Operations accounts, actual password Auth/JWT/PostgREST/RLS/RPC, AR and EN desktop/mobile contexts, lost create/approval responses, one request/audit/notice, and expired/changed/outsider/revoked cases. Exact source/evidence hashes and review receipts belong to Task265. A local result proves neither Vercel Preview nor Production, provider template approval/delivery, current availability, cancellation terms, payment or booking.
