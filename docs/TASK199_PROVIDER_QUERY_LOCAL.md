## What changes

`DIR3COM_WHATSAPP_DELIVERY_MODE` defaults to `webhook`. That path still requires its signing secret and retains raw-body HMAC verification and its current receipt gates. Explicit `provider_query` configures the same existing target sender without requiring a webhook signing secret or inventing a webhook resource ID. It permits only `operations.created` and never the generic dispatcher. API key, sender, exact approved template, site and authenticated worker remain required. No credentials or flags are set by this candidate.

Both runtime and SQL bind the delivery mode. A query sender cannot use a webhook window, and a webhook sender cannot use a query window. The new service-only `open_kapso_drive_whatsapp_provider_query_window` uses the same target/consent/future-request/window guards; it does not enroll, enable capture/send, backfill or reset attempts/budget. The reviewed final intent implementation is moved unchanged behind a private mode wrapper, preserving its outbox-lock/clock recheck and rollback on expiry.

Sending is still one target claim, durable begin intent, one template POST and the existing `finish_drive_whatsapp` transaction. WAMID and row outcome are stored together by that DB transaction. Provider acceptance and DB completion are not a distributed transaction. Response loss or a failed/unknown finish retains the durable intent and cannot regain send eligibility. A response lost after a committed finish can be reconciled using the saved WAMID. A missing WAMID cannot be guessed, listed or retried by this feature.

## Delivery read

Authenticated `POST /api/internal/drive-whatsapp/reconcile-target` accepts the same five fields as dispatch-target: requestId, outboxId, recipientUserId, category and language. It accepts no WAMID, provider URL or window override from its caller. A service-only RPC reserves a durable query lease for the selected active query window and the exact persisted WAMID, phone and sender. No fallback row is chosen.

One invocation makes at most one fixed-origin GET to the documented [Get message by ID](https://docs.kapso.ai/api/meta/whatsapp/messages/get-message-by-id) endpoint:

`https://api.kapso.ai/meta/whatsapp/v24.0/{stored_sender}/messages/{encoded_stored_WAMID}?fields=id,to,kapso(direction,status,processing_status)`

Only HTTP200 JSON with exact WAMID, numeric recipient match and outbound direction is an observation. The sender is pinned in the DB lease and request path. The official GET response schema declares neither kapso.phone_number_id nor kapso.passive, and neither is requested by fields. Defensive checks reject contradictory extras if returned; their absence does not independently verify the sender or prove non-passive delivery. Synthetic tests of these extras are not provider-contract evidence. See the [official OpenAPI schema](https://docs.kapso.ai/api/meta/whatsapp/openapi-whatsapp.yaml), WhatsappMessageResponse and getMessage. There is no redirect. BSUID-only identity is not mapped to a phone. Status is restricted to sent/delivered/read/failed. Raw text, contacts, headers, processing data and response bodies are neither persisted nor returned. The complete HTTP/body/DB operation has a six-second application deadline and an8192-byte provider-body limit; DB query RPCs have one-second lock and four-second statement limits.

SQL persists a maximum of three reservations per window, including uncertain reservations. It enforces a five-second minimum cooldown, an eight-second query lease and the original maximum ten-minute window. Only one query lease can be active. A crashed reader consumes its reservation; any later bounded read uses a different token and cannot commit an older result. No polling loop, timer job, cron, Edge Function or new message retry is installed.

404,429,5xx, malformed/oversized bodies, wrong identities or missing WAMID do not prove delivery. The authenticated worker receives only fixed reason codes: HTTP_NOT_FOUND, HTTP_RATE_LIMITED, PROVIDER_UNAVAILABLE, HTTP_UNCONFIRMED, BAD_BODY, PROVIDER_ERROR, IDENTITY_MISMATCH, UNSUPPORTED_STATE or TRANSPORT_UNCONFIRMED. Uncertain lease/identity/persistence and elapsed deadlines have separate QUERY_* codes alongside the existing generic503 error. No raw provider/DB exception is copied. The SQL outcome remains observed/unconfirmed; these diagnostic reasons are not a new delivery state or persisted provider payload. An unconfirmed query never changes accepted to failed/delivered and never sends a message. A verified failed status is recorded without adding a retry policy. Completion is fenced by query token, stored WAMID, sender, phone and target association; existing receipt monotonicity prevents regressions, including concurrent webhook/status observations. `recorded` means an observation was durably ingested, not necessarily delivered: the authorized delivery-state view determines actual progression.

Stop and expiry block new network reservations. An in-flight read may complete, like an in-flight callback; neither an application response nor stop guarantees cancellation of already-started I/O. Query windows contain no webhook ID and report no provider-deactivation work for themselves. Webhook windows preserve their inherited deactivation_required behavior: repeated stop preserves stopped_at/stop_reason and disables sending, but reasserts deactivation_required=true even after an external bookkeeping clear. There is no implemented acknowledgment/clear API in this source; no new acknowledgment contract is introduced. Historical webhook-create Unknown and consumed grants are unchanged; this feature does not retry or resolve that resource operation.

## Recovery evidence limitation

After a validated provider acceptance, finish receives the exact outboxId/WAMID pair. If the DB commit succeeds but its reply is lost, the pair is recoverable from that row without another POST. If the commit does not persist, the current generic error does not retain an independent pair. This operational gap predates provider_query and remains unresolved here. The existing lib/security/safe-logger.ts writes sanitized metadata to console; it truncates strings and redacts number patterns. Source inspection establishes neither a private recovery destination nor its access/retention guarantees. Do not weaken that sanitizer, add a destination/service or emit a raw recovery pair into unverified logs. The required choice is to identify an already existing, suitably restricted destination and demonstrate its privacy and lossless handling of these validated identifiers, or separately approve a different recovery design. No raw recovery logging or client exposure is added. Even suitable logging cannot eliminate the provider/DB crash gap, prove delivery or authorize resend.
